# ZenoBench 评测指标与成功／失败分类

日期：2026-10-20。

本文仅定义后续实验采用的评测指标、成功分类和失败归因。**当前只补充文档，不要求修改评测代码、启动实验或重新运行历史记录。** 指标定义不代表已有实验结果，也不代表相关统计已经全部实现。

更新（2026-10-20）：统计层已按本文接入评测代码，实现范围与暂不能可靠自动判定的部分见第 6 节。仍未启动新的 VLM 实验。

已有的技能验证和 Scripted 物理路线验收属于可行性证据，与正式 VLM / Planner 对比实验分开报告。

## 1. 必须区分的三个层次

| 层次 | 回答的问题 | 证据 |
|---|---|---|
| 场景与路线可行性 | 这个条件是否真实成立，是否存在能完成目标的路线？ | Scripted 完整物理执行、失败原因、恢复前后状态、最终 GT Goal |
| 上层决策能力 | 模型能否自主探索、选择技能、恢复或选择替代方案？ | 相同观测权限下的 Planner 闭环运行 |
| 下层执行能力 | 给定合理调用，Controller / Contract 是否执行成功？ | 参数与前置条件、实际接触和状态变化、后置条件 |

Scripted 路线通过只能作为物理可行性证据，不能算 Agent 自主恢复成功。GT Oracle 使用的信息与执行设置若不同，单列为能力参考，不直接用其差距证明 VLM 恢复收益。

## 2. 六个核心指标

| 指标 | 评测内容 | 判定与报告要求 |
|---|---|---|
| Task Success Rate（TSR） | 端到端任务完成能力 | 最终满足全部 Goal 和原任务约束，不要求匹配预写路线 |
| Planning Correctness | 高层 Skill 选择与组合 | 检查技能、参数、对象、依赖和执行顺序；物理失败不自动等于规划错误 |
| Functional Substitution Success Rate（FSR） | 功能替代能力 | 在需要替代且存在已验证合法替代方案的条件中，使用合法替代方案并完成原任务 |
| Execution Recovery Success Rate（ERSR） | 实际执行失败后的恢复 | 真实执行失败后，上层自主处理状态，最终完成原任务 |
| Long-Horizon Robustness | 多步与组合挑战下的稳定性 | 分任务长度、物体数量、实际房间转换及挑战组合报告 TSR，不凭调用次数宣称长时序 |
| Execution Efficiency | 完成任务的成本 | Skill Calls、恢复额外调用、无效重复、实际导航距离和模拟时间；与 TSR 一起解读 |

论文主表优先报告 TSR、FSR、ERSR；其余作为补充分析。尚无可靠数据的指标显示 N/A，不填 0、不编造数值。

### 2.1 Task Success Rate

`TSR = 成功完成的 Episode 数 / 实际完成评测的 Episode 数`

- 分母是 Episode，不是任务类型数。未运行配置不进入分母。
- 只有明确的基础设施异常可以单列为 System Error；不能把模型的非法调用或错误计划排除以提高 TSR。
- 同时报告计划数、启动数、有效评测数和系统异常数，避免只展示筛选后的成功率。
- 报告总体 TSR，以及按任务等权、按条件等权的平均值；给出样本数。
- 最终状态按现有物理 Verifier 判定，保留稳定放置、位置、容器、温度和设备状态等要求，不放宽物理条件。
- 中途发生失败或掉落不必永久判任务失败：若之后真实恢复且满足全部最终约束，可成功；中途掉落另记事件。确有不可逆安全约束的任务按其明确约束处理。

### 2.2 Planning Correctness

不要通过与唯一正确 Skill Sequence 比对评分。

- 检查技能是否存在、参数是否合法、目标是否允许操作、必要依赖是否满足。
- 在调用时记录合理性为 `valid`、`invalid` 或 `undetermined`，以及证据；证据不足不强行判错。
- 如报告比例，使用 `valid / (valid + invalid)`，同时报告 `undetermined` 和判断覆盖率。
- 目标暂时不可见、不存在、需要搜索，要结合任务与观测历史分析。
- 合理探查失败和按设计尝试一个无法事先判断的操作，不自动归为上层错误。
- 只有执行后才暴露的碰撞、滑落等，不能利用事后 GT 倒推为模型本应知道的规划错误。

### 2.3 Functional Substitution Success Rate

`FSR = 合法替代并最终完成任务的 Episode 数 / 预先登记且已验证需要替代、存在合法替代路线的有效评测 Episode 数`

- 分母根据场景与任务语义预先确定，不按某个模型是否尝试了原方案来筛选。
- 提前观察到原方案不适用，直接选择合法替代方案，也算成功，不强制制造一次失败。
- 分开记录 `substitution_selection` 与 `task_success`：选对替代方案但搬运掉落，是选择正确、端到端失败。
- 允许一个场景存在多个合法替代方案，不能只认预写脚本中的那个。
- `unknown` 不等于 `absent`：暂时没观测到 Cup，不能据此在判定中认定 Cup 不存在。

任务指令的条件语义必须落实到 Goal Evaluation：

| 指令语义 | 正确判定 |
|---|---|
| Cup 或 Mug 都可以 | 两者均合法，不要求先尝试 Cup |
| 没有 Cup 才用 Mug | 按任务规定的缺失条件判断，不得无条件接受 Mug |
| 篮子不在时改用托盘 | 篮子存在时不能绕过偏好，总是用托盘仍判成功 |
| 从容器中选择合适的一个 | 直接选择合适的大容器有效，不要求先往小杯里放 |

条件合法性由评测端检查，不向 Planner 暴露隐藏存在性或正确分支。不能扩大“不可用”的含义来接受原指令不允许的替代方式。

### 2.4 Execution Recovery Success Rate

`ERSR = 真实执行失败后最终完成原任务的 Episode 数 / 发生真实执行失败的有效评测 Episode 数`

必须另记两个结果：

- **局部恢复成功**：辅助操作实际改变了失败相关状态，原先失败的操作或子目标随后成功。
- **恢复后任务成功**：上述恢复后，整个原任务最终完成。

例如：

```text
Pick 失败 → Separate → Pick 成功 → 搬运时滑落，未恢复
```

记录为局部恢复成功、最终任务失败；最后失败原因是搬运执行失败，不能把它写成 Separate 选择错误。

要求：

- `POLICY_FAILED` / `SUBSKILL_FAILED` 等错误码只是线索；核对实际失败的子步骤及状态证据。
- Search / Look 解决观测问题，单列观测恢复；Uncover 解决前置状态，单列前置条件恢复；二者不混入物理执行 ERSR。
- 允许不同辅助技能和有效操作组合，不把匹配预写 Fallback 名称作为成功条件。
- 原操作没有恢复，但合法 Alternative 完成任务时，记录 Alternative 成功，不假称原操作已经恢复。
- 多次失败按事件分别记录；一个 Episode 可以局部恢复多次，最终仍失败。事件级和 Episode 级比例分开，必须标明分母。
- 盲目重试偶然成功可以计入最终 TSR，也可进入“失败后完成”的宽口径统计；但没有状态修复证据时，不能记作已验证的辅助操作恢复。报告 `retry_only` 或 `mechanism_unverified`。
- 各模型实际遇到的失败不同，因此 ERSR 需要同时报告失败发生率、失败类别、样本数和故障条件上的 TSR，不能只比较一个条件恢复百分比。

可选后续实验：通过真实动作前缀重放重建同类失败状态，让不同 Planner 接管。不为本轮新增一套复杂的物理快照系统，不靠假状态或伪造执行结果生成恢复样本。

### 2.5 Long-Horizon Robustness

先作为分组分析，不强造一个综合分数：

- 按预先定义的任务复杂度、操作物体数、房间转换和挑战组合报告 TSR。
- 记录实际导航距离、房间转换和 Skill Calls；缺数据时说明，不凭任务文字估计。
- 区分短任务与多步生活任务，不通过插入无意义动作增加长度。
- 比较正常、单一挑战、组合挑战的表现；任务确实发生状态变化才统计对应挑战。

### 2.6 Execution Efficiency

- 报告总调用、额外恢复调用、无效重复、实际导航距离和模拟时间。
- 模拟时间与程序耗时、模型响应时间分开，避免机器速度干扰动作效率。
- 成功 Episode 的成本单列；失败 Episode 的成本和 TSR 也要显示，不能靠提前放弃获得高效率评价。
- 相同 Skill 和参数的再次调用不必然是无效重复：期间若相关状态已经改变，可以是合理重试。
- 正常场景中不必要的 Expose / Separate 等计入额外开销；符合约束时不直接判任务失败。
- 参考路线只称“已验证参考路线”，未经证明不称最优；具有 GT 特权的 Oracle 不能作为同信息条件下的最优效率证明。

## 3. 成功分类

只对最终成功的 Episode 使用下列类型：

| 类型 | 标准 |
|---|---|
| Direct Success | 正常执行或必要探索后完成，没有发生需要恢复的失败，也没有使用语义替代方案 |
| Fallback Success | 经已验证的辅助操作恢复后完成；附观测、前置状态或物理执行子类型 |
| Alternative Success | 使用合法替代物体、工具、容器、目的地或方法完成；可主动选择，也可在失败后选择 |
| Combined Success | 多种恢复机制或 Fallback + Alternative 组合后完成 |

类型不能完全由路线名称推断。单独记录 `had_failure`、`local_recovery` 和 `used_substitution` 等事实，避免丢失主动替代与失败后替代的差别。

若完整最终轨迹含探索，但没有操作失败，不能因为调用过 Search 就记为失败后恢复。

## 4. 失败分类与责任归因

| 类型 | 判定标准 | 不应误判的情况 |
|---|---|---|
| Planning Failure | 上层选错技能、参数、对象，或顺序错误、遗漏依赖 | 合理调用遭遇不可预知物理失败 |
| Exploration Failure | 未能找到必要对象或目的地，导致任务不能完成 | 一次 Search 没找到但后续找到 |
| Substitution Failure | 存在已验证合法 Alternative，但上层选错或未使用而失败 | 选对替代方案后下层执行失败 |
| Recovery Failure | 存在可行恢复方式，但上层无效重复、选错辅助操作或放弃 | 正确辅助操作本身物理执行失败 |
| Low-Level Execution Failure | 调用合理、必要前置条件满足，Contract / Controller 实际执行失败 | 上层在手占用、门未开等不满足条件时强行操作 |
| Feasibility Unverified / Issue | 缺少可信完整可行性证据，或证据表明当前条件超出现有能力 | 单次 Oracle 失败不自动证明场景不可完成 |
| System Error | 仿真或外部接口、服务基础设施异常 | 模型输出非法调用不能直接作为系统异常排除 |
| Undetermined | 当前状态或日志不足，无法可靠判断 | 不为统计整齐强行归入上层或下层 |

归因原则：

- 错误码不等于责任。读取嵌套 Contract 的实际失败步骤，结合调用前状态判断。
- 逐事件记录直接原因；最终 Episode 记录阻止目标完成的主要原因，并保留其他事件，不重复累加为多个失败 Episode。
- 上层先犯错导致后续碰撞，应保留因果链，不能只因最后有 `POLICY_FAILED` 就全部归咎下层。
- 成功 Episode 也可以包含失败事件；不要抹掉被成功恢复的下层失败。
- 一个 condition 有一条可行路线，不意味着它声明的所有 Fallback / Alternative 路线都已经通过；逐路线保留验收状态。

## 6. 实现状态（2026-10-20）

统计层已接入（离线计算，不改观测权限、底层技能、物理判定和自动恢复关闭设置）：

- **入口**：
  - `python benchmark/evaluate.py --tasks ... --runs DIR... [--batch FILE...]`；
  - `run_episode.py --batch` 跑完后自动对 `--out` 目录运行同一评测，写出 `EVALUATION.md`、`metrics.json` 和 `metrics.facts.jsonl`。
- **代码**：
  - `benchmark/metrics.py` 负责逐调用记录、事件、Episode 事实和六项指标聚合；
  - `benchmark/eval_semantics.py` 存放各任务替代语义，Planner 侧不导入；
  - `benchmark/tests/test_metrics.py` 和 `test_session_eval.py` 是离线测试。
- **日志**（`eval_log_version` 2）：
  - 每次调用记录 Skill、参数、反馈、调用前后 GT 状态摘要（`state_before`/`state`）、`eval`（最深一层失败子调用链、错误码、失败检查）和 tick；
  - 闭环 Planner 另记 `planner_s`。
  - 这些字段只写日志，不进入 `observe()` 或反馈。
- **旧日志兼容**：
  - 缺 `state_before` 时用上一调用的 `state`（第一步用初始位置）；
  - 缺 `eval` 时从嵌套错误文本解析失败子步骤；
  - 缺的数据显示 N/A。
  - 历史结果不改写。

| 规范条目 | 状态 |
|---|---|
| TSR：计划/启动/有效/系统异常数，总体、按任务、按条件等权 | 已实现；计划数需 `--batch` 或 `--planned`，否则 N/A |
| TSR 按指令语义 | 已实现：Cup/Mug、Pen/Pencil、篮子/托盘由 GT 初始状态（物体是否在本 Episode）判定，不看 Planner 是否观测到；“任选其一”“装得下的容器”均合法 |
| Planning Correctness valid/invalid/undetermined | 已实现保守规则；只把接口错误和观测里可见的手部状态前置失败判 invalid，其余不确定 |
| FSR、选择与端到端分开、主动替代 | 已实现；分母需已验证的替代路线 |
| ERSR、局部恢复与任务完成分开、观测/前置/物理分开、retry_only、mechanism_unverified | 已实现；状态证据仅限 watch 列表中的物体、手、底座和温度 |
| Robustness 分组 | 已实现；房间转换按每次调用结束时的底座位置统计 |
| Efficiency | 已实现；导航距离是调用间直线距离之和（下界），不是实际路径长度 |
| 成功分类、失败归因 | 已实现；Scripted/Oracle 不归入上层规划、恢复或替代失败 |

暂不能可靠自动判定（输出 `undetermined`/N/A 或需人工复核）：

- **实际导航路径长度**：没有逐帧底座轨迹，只报下界。
- **模型响应时间**：只有新版闭环日志才有；旧日志和 Scripted 为 N/A。
- **非 watch 物体或铰接状态带来的恢复证据**（如门、盖子未在 watch 中）：记 `mechanism_unverified`，不算已验证恢复。
- **规划合理性中的语义判断**：例如该不该先 Search、某次 Uncover 是否必要。这类调用记 `undetermined`，不用事后 GT 倒推。
- **全部调用都成功但 Goal 不成立**：例如放下后滑动。规划遗漏与静默物理失败无法区分，记 `undetermined`。
- **System Error**：只把 crash/incomplete 当系统异常并排除出分母。模型策略代码抛出的异常也会落在这里，需人工复核 traceback。
- **因果链**：上层错误引起的后续物理失败，只保留逐事件原因，不自动推断因果。
- **“篮子不在”**：只按“物体不在本 Episode”判定。若以后出现“篮子在别处”的变体，需在 `eval_semantics.py` 增加位置条件。
