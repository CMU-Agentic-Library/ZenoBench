# 物体与家具注册表：按功能判定替代（2026-11-24）

起因是 Katia 的建议：哪些东西能互相替代，应该有依据可查，不能只靠 VLM 的常识或我们手写的清单。按讨论的结论，这里做的是"窄版本"：

- 只收录仿真里能用物体状态核对的功能和属性。没有液体量、温度耐受数值、容量毫升数这类模拟不出来的东西；"能盛液体"只作为器皿的语义属性，用来判断替代是否合理，仿真里不倒水。
- 注册表默认只用于评测，不给 agent 看。`object_registry.agent_card()` 可以把它导出成文本，留作以后的消融实验："把注册表给 planner，分数能涨多少"。
- 不改技能，不改现有任务设计。手写的 tier 保持原样，注册表负责逐个对照，把差异列出来交给人决定。

## 组成

| 文件 | 内容 |
|---|---|
| `registry/objects.yaml` | 47 种可移动资产：分类（大类 → 子类 → 资产种类 → 场景实例）、功能、人工标注的属性（材质、易碎、可接触食物、可进微波炉、可上灶、儿童用、有把手、带盖） |
| `registry/furniture.yaml` | 家具和电器按类型标注，按支撑面种类（顶面、搁板、柜内）给功能，例如可放置、餐桌、厨房台面、展示、收书、柜内收纳、冷藏、灶台加热、微波加热。共覆盖 45 件家具、116 个支撑面 |
| `registry/roles.yaml` | 34 个替代角色：19 个物体角色、11 个位置角色、1 个电器角色、3 个点名角色。每个角色写明替代物出现在哪种条件里、理想物、必需功能、几何约束和加分项 |
| `object_registry.py` | 读注册表并做判定。几何属性不手写：物体的尺寸、开口、深度、质量、能否抓取，取自 `annotations/assets.json`，和仿真生成物体用的是同一份数据；支撑面的高度、大小、净空、所在房间、是否在柜门后，取自场景标注 |
| `affordance_check.py` | 拿注册表逐个对照手写 tier，输出 `AFFORDANCE_CHECK_zh.md` 和 `AFFORDANCE_CHECK.json`；加 `--check` 参数时，报告过期就报错 |
| `tests/test_object_registry.py` | 检查注册表完整、词表封闭、角色和 `tasks.json` 对得上、放宽规则里的手写表都合法、报告是最新的 |

## 判定规则

一个替代物 o' 对角色 g 合法，要同时满足两点：

- **功能**：A_required(g) ⊆ A(o')。`requires` 里的功能要全部具备；`requires_any` 里的功能至少具备一项。
- **约束**：满足角色的约束：
  - `fits`：装得下指定物体（开口留 5% 余量）
  - `covers`：盖得住指定锅的开口
  - `taxonomy_any`：子类在给定范围内
  - 位置角色：`room_of` 同房间，`near` 在某个距离以内
  - 电器角色：容器材质可以进这个电器

替代关系由任务决定，不是固定的一对一映射。同一个马克杯，在 T30 是合法的盛汤器皿，在 T15 就不能当锅盖。

合法的东西再按等级排序：

| 等级 | 含义 |
|---|---|
| 0 | 不合法 |
| 1 | 合法，但开局时被占用：里面装着东西、放在别的东西上，或者名字表明在用/装满 |
| 2+k | 合法且空闲，满足 k 个加分项 |
| 10 | 理想物（或理想位置），而且可用 |

"被占用"是从开局摆放自动算出来的：容器里有东西，或者锅盖盖在另一口锅上、苹果放在别人的盘子里。台面摆得有多满算不出来，所以理想位置被占满的布局，要在角色里用 `ideal_unavailable` 显式写出来。

## 对照结果（详见 `AFFORDANCE_CHECK_zh.md`）

一共对照了 154 个（角色，布局）组合。`loosen_1124.py` 里手写的三张放宽表共 61 条，全部能由注册表推出，没有不合法的，也没有没被角色覆盖的。

### 处理原则（11-24 用户）：按原标准，不改分

注册表只做校验和记录。下面这些差异都保留手写 tier 的原判，`tasks.json` 不因注册表改动。

- **书当锅盖**：T09 `lid_on_spoon_away`、`lid_missing`，T15 `lid_elsewhere__dining`、`no_lid`，共 4 个布局，原判 0.3 或 0.6 分。注册表的判断是书的窄边 14 cm，锅口 23 cm，盖不住，记为不合法。保留原判。
- **盘子盛汤**：T18 `one_bowl` 2 个布局，T30 共 8 个布局，原判 0.3 或 0.6 分（差的选择但算完成）。注册表的判断是盘子不能盛液体。保留原判。
- **T04 杯子排序**：`plastic_only`（冰柠檬水，要 cup）是儿童塑料杯 1.0、马克杯 0.6；`no_cup`（喝茶，要 glass）是马克杯 1.0、儿童杯 0.6。指令点名的器皿类型不同，各自按原判。
- **点名物给部分分**：T01 `which_book`、T28 `where_his_cup_is`、T14 `next_in_series`，共 7 个布局。拿错但同类的仍得 0.3 或 0.6 分，保留原判。
- **候选放宽**：37 个布局里有功能上合法、但手写没接受的东西或位置，例如 T11 其它空碗装水果、苹果放冰箱、T17 用盘子盖锅。只记录在 `AFFORDANCE_CHECK_zh.md`，不应用。

论文里可以把这些差异作为"按功能判定和人工判定的差别"来报告。"无效替代"类的评测，用注册表的不合法判定单独统计即可，不需要改主分数。

## 局限

- 台面摆得多满不建模；理想位置被占的布局要手写 `ideal_unavailable`。
- 场景标注里的房间名不一定反映房间用途，例如孩子的书桌被划在 living_room_0_1，厨房是开放式的。因此厨房类角色不用同房间约束，"床边"改用距离判断。
- "能盛液体""可进微波炉"是语义属性，仿真不模拟液体，也不模拟材质受热。
- 注册表只负责校验和记录，`tasks.json` 仍由手写 tier 加 `loosen_1124.py` 生成（11-24 定：按原标准）。

## 运行

```
python benchmark/v6/affordance_check.py          # 重新生成对照报告
python benchmark/v6/affordance_check.py --check  # 报告过期则报错
python -m pytest benchmark/v6/tests/test_object_registry.py
```

修改 `registry/*.yaml` 或 `tasks.json` 之后，都要重跑对照，报告随代码一起提交。
