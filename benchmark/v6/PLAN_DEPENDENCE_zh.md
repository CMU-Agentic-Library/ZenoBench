# 固定路线迁移与信息依赖：符号筛查报告

生成：`python benchmark/v6/plan_dependence.py`，数据在 `PLAN_DEPENDENCE.json`。只用符号状态，没有 planner，也没有物理仿真。结果只用来筛查任务，**不据此自动删除 variant**。

## 怎么做的

**执行层**：用 `oracle_check.World` 的符号状态逐步执行，并打开 benchmark 的观察门控。
- 技能参数里的物体必须先看见过。开局能看见的，是起始房间里没被遮挡的东西；之后通过 look、explore、走到跟前、在正确房间 search 来看见。
- `search` 只在给定房间里找：会打开那个房间里关着的柜子（真实技能也是这样），但看不到盖子下面的东西，也不会直接用物体的真实位置。

**算“通过”**：每一步都合法，且符号层能判断的目标全部满足，包括过程要求 `never_picked`。

**几何条件单独列出，不算通过**：只能靠几何判断的条件一共 283 个：upright 188、clear_of 42、away_from_edge 32、front_visible 8、squared 6、same_arrangement 3、visible_from 2、grouped 2。另外，`fully_inside` 在符号层只检查“在容器里”，“是否完全放得进去”还要靠几何，比如 T22 托盘被书占满时能不能放进苹果。**符号通过不等于物理验证通过。**

**候选路线**：
1. 对照 variant 的参考路线，迁移到同一任务的其他 variant；
2. 同一 variant 各布局的参考路线，相互迁移；
3. 对每个多布局 variant，检查它自己各布局的路线加上对照路线里，有没有一条能通过它的全部布局（固定序列）。

**迁移失败的原因**（按第一个问题归类）：
- `resource_missing`：路线用到了这个任务里的某个物体，但这个布局里没有；
- `unknown_object`：用到了这个任务从来没有的名字（本次没有出现）；
- `not_observed`：被观察门控拦下，没见过就去用；
- `argument_mismatch`：这一步和当前状态对不上，比如不在跟前、门关着、search 的房间不对；
- `goal_not_met`：每一步都合法，但目标没达成。

## 结果

参考路线：278 条全部通过，开着观察门控也全部通过。

之前有 16 个 variant 的参考路线开局就直接去拿另一个房间的东西，门控下会被拒。现在生成目录时，`observe_first` 会在第一次用到没见过的物体之前，自动插入“走到它所在的家具 → look”；如果物体在地上，就改成探索它所在的房间。

| 诊断 | 结果 |
|---|---|
| 对照路线迁移到其他 variant（248 个布局） | 能通过 54，目标不满足 92，没观察到 60，资源缺失 36，参数不匹配 6 |
| 同一 variant 的布局之间互迁 | 能通过 31，目标不满足 90，参数不匹配 85，资源缺失 62，没观察到 8 |
| 有一条固定序列能通过全部布局 | 79 个多布局 variant 里有 10 个 |
| 隐藏状态分叉（关键观测前看到的一样，路线互迁都失败） | 79 个里有 46 个 |

**有一条固定序列通过全部布局的 10 个**（需要逐个检查，不是结论）：
- T01 `table_seats`、`which_book`
- T05 `check_desk_first`
- T06 `seen_from_bed`
- T09 `x6_gd_tomato_elsewhere`
- T13 `copy_the_setting`
- T14 `next_in_series`、`within_kids_reach`
- T16 `everything_near_the_edge`
- T27 `two_leftovers`

其中好几个的难点在几何或指代上，符号层看不出来：
- T01 的空位选在哪；
- T13 的摆法要和示范一致；
- T16 的离边缘多远。

T27 `two_leftovers` 的固定路线本身就会先 look 桌子和灶台，所以“固定序列通过”不代表不需要看。

**怎么解读**：“固定序列能通过”只说明存在一条跨布局都能用的技能序列，这个 variant 可能缺少规划分支，值得再看一眼。它不说明这个 variant 不需要观察和推理，原因有两个：
- 序列里的 look、search 本身就在用看到的信息；
- 在同类物体里选哪一个，符号层是按名字选的。

反过来，“隐藏状态分叉”也只证明后续计划必须不同，不证明 planner 真的会去观察。这要跑真实 planner，并做完整观测 / 缺少关键观测 / 固定计划三组对照。

## 新增和修改的困难 variant：关键观测、隐藏事实、计划分叉

五个都通过了配对测试（`tests/test_oracle_check.py::test_dependent_decisions_branch_on_what_is_found`）：存在关键观测前看起来一样的布局对，且各自的路线放到对方布局上都失败。也都没有一条固定序列能通过全部布局。

| variant | 类别 | 关键观测 | 隐藏事实（布局） | 观测后的计划分叉 |
|---|---|---|---|---|
| T21 `tissue_or_sponge`（修改） | T | 打开第一个矮柜，再打开第二个 | 纸巾在第一个柜 / 第二个柜 / 家里没有；岛台上始终有海绵 | 第一个柜有：拿纸巾，海绵不拿；第一个空：继续开第二个；两个都空：拿海绵。柜门都关好 |
| T22 `tray_elsewhere`（新增） | A+T | 到西边餐厅看托盘 | 托盘里有一个橙子 / 被四本书平铺占满 | 有橙子：苹果直接放进去（能共存，不挪）；被书占满：先把书放回书架（任何书架都算），再放苹果。果汁进冰箱 |
| T25 `cups_for_two`（新增） | T | ①看客人桌上有几个杯子；②打开矮柜看库存 | 桌上 1 个 + 柜里 1 个 / 0 + 1 / 0 + 2 / 2 + 1；后两种开柜前一样 | 缺 1 个且柜里有：补 1 个普通杯；缺 2 个、柜里只有 1 个：普通杯加餐厅的马克杯；柜里有 2 个：拿两个普通杯；桌上已经 2 个：只送饮料 |
| T28 `where_his_cup_is`（修改） | T | 到台面看杯子 | 他的塑料杯在台面上（和别人的杯子一起）/ 在矮柜里 | 台面上有：直接拿；只有别人的：打开矮柜找，拿出来关门 |
| T30 `bowls_in_cabinet`（修改） | T | 打开矮柜 | 柜里两个碗 / 一个碗；家里没有别的碗 | 两个碗：拿三个碗，马克杯不算；一个碗：两碗加马克杯（指令允许）。都送到岛台，柜门关好 |

**各 variant 的设计说明**

T22：
- 挪开托盘上的书，属于现有的局部条件 `destination_full`（A）。
- “果篮不在，去另一个房间找替代容器”是独立的 Task 要求，所以归为 A+T，没有把单纯清空目的地当作 Task 难点。
- 原来还有一个“空托盘”布局，它和“有橙子”布局的参考路线完全一样，不构成分叉，被静态检查拦下，所以删掉了。

T25：
- 柜里的库存开柜前看不见。
- 场景原有的三个普通杯（在小厨房和西边餐厅）在这个 variant 里移除了。这是写在场景配置里的，不是在目标里藏白名单；保留它们会让“柜里只有 1 个”的分支失效。
- 留下的每一个杯子和马克杯，目标的计数都认（`test_every_vessel_in_the_house_counts`）。
- 普通杯优先：要求的普通杯数量是 min(2, 现有普通杯数)。
- 最后正好两个杯子（`count_on_at_least` 加 `count_on_at_most`），原有的杯子不动（`near_start`），饮料立着送到，柜门关好，手空。
- 原有 T25 的 variant 全部保留。不涉及冷却，也不倒饮料。

T30：
- 指令改成“碗不够的话，马克杯也行”，和目标一致。
- 柜里有两个碗时，马克杯不算；只有一个碗时，任何杯子或马克杯都算。

**分类边界**
- T27“冰箱满了”撤下了。挪开占位物属于 `destination_full`（A）；判断“哪个可以挪出去”是在工作点就能完成的短判断，不算独立的 Task 要求。按规则不能单独作为 A 留下。
- T12 容量 / “大件先放”暂缓，等真实几何和物理验证。

## 泄露审计

**检查了**：
- env_service 开局消息；
- run_episode 的 recovery planner 输入：指令、技能列表、观察；
- benchmark profile 的 `gt_objects`、`task_status`、`mask_feedback`；
- 静态已知地点：只有家具和房间，没有物体；
- 指令：不含 variant 或布局名，每个布局的指令相同。例外是 T01 `which_book`，指令本身就是线索（客人说昨晚在哪儿看的书），这是设计如此；
- oracle 路线和配置注释：以上面向 planner 的字段里都没有。

**发现一处泄露**：`env_service/worker.py` 开局发给 HTTP planner 的 `episode` 元数据，包含 variant 名（带布局名）、conditions 和 seed；如果 planner 手里有 `tasks.json`，用 seed 就能查出布局。这个文件是 muqingj 的，需要他改成只发指令和观察，元数据只留在 `config.json`。

**另外**：72 个 variant 的物体实例名带含义（比如 `full_bowl`、`spare_mug`、`stock_cup_1`）。planner 看到的 `visible_objects` 用的就是实例名，所以应该在观察层把实例名匿名化，比如统一成“类别_编号”。这一项也在 muqingj 的代码里。

## 还没做的

- **物理验证**：172 个 variant 都只做了静态检查和符号检查。新物品和新动作的抓取、放置都没验证，包括托盘上平铺的书、柜内的杯子和碗、冰箱等。
- **几何条件**：283 个几何条件，加上 `fully_inside` 的“完全放得进”，要等仿真来判断。
- **真实 planner 对照**：完整观测 / 缺少关键观测 / 固定计划三组对照实验，要等有 planner 和物理之后再做。
- **泄露修复和名字匿名化**：见上文，需要 muqingj 改。
